# M3 失败现场与直接合盖路径

**事故告知（2026-09-17）：暂停所有双外屏实验。** M3 用户在 v0.4.0 实验后反馈：退出应用后，真实合盖也只亮一台外屏。不要重新采样、反复切换显示状态或调用旧版实验／恢复接口。含实验功能的 v0.2–v0.4 发布已撤回。

报告显示，新增外屏在禁用后丢失了可核对的身份，后续启用请求未执行。原有的失败处理请求恢复内屏，却不能据此确认外屏已回到实验前状态。**内屏恢复不等于外屏基线恢复。** 用户随后确认：重启后保持 OpenClam 未运行，真实合盖双外屏已恢复。这不证明具体底层根因，也不表示开盖双外屏实验已修复；实验继续暂停。这一过程与本次故障的具体因果关系仍未确认。

已受影响时，先保存工作、退出 OpenClam，断开外接显示器后重启 Mac，并保持应用不运行；再接上电源与外接显示器，合盖检查两台是否都有实际画面。本次重启恢复的反馈不保证其他故障也能恢复。若仍异常，保持应用退出并反馈结果，不继续测试。不要进行 SMC／NVRAM 重置、删除显示配置或再次调用私有显示接口。

以下仅保留事故前的实现与验证记录，不是继续实验的操作指南。此前 M4 的通过结果不能覆盖 M3，也不能代替 M3 的实机恢复验收。

## 综合采样记录的语义

v0.4.0 采样器在后台约每 2 秒读取显示端点、framebuffer、电源和端口状态，同时记录显示配置回调、系统睡眠／唤醒事件和应用操作标记，最多运行 3 分钟。此处说明已有报告的解释边界，当前不要求重新采样。

样本起止时间、配置通知和操作标记使用包含睡眠的连续时钟；通知时间表示应用收到回调的时刻。端口事件时间保留驱动原值，单位未知，不能直接与时间线秒数相减。实验日志原有时间精度为秒。保存时刷新末尾实验日志，并单独记录其采集时间，避免丢失采样到期后才提交的反馈；原采样结束时间不变。

采样自身只读，不会自动改变显示状态，也不会上传数据。退出应用会终止采样；系统睡眠期间也可能出现采样空档。导出报告包含多层状态时间线和经过字段筛选的实验报告。缺失或读取失败的字段标为 `unknown`，不推断为关闭、零或不存在。

这些记录用于对比同一机器上失败与成功状态的差异，不能证明物理画面或色彩。显示器出现在系统桌面、鼠标坐标可进入对应桌面区域，都不能单独证明该物理屏幕收到信号；仍需记录用户在第二台屏幕上实际看到的画面。

## M3 报告确认的事实

报告来自基础款 M3 MacBook Air（Mac15,12），macOS 26.5.2（25F84），保留了 v0.3.1 和 v0.3.2 两次实验：

- 合盖请求后出现第二外屏；它通过 `IODisplayLocation` 唯一映射到启动前固定的内屏共享 framebuffer，选择请求没有跳过或发往另一台外屏。
- `IOMobileFramebufferSetDisplayDevice(2)` 返回 `0x00000000`，但用户仍报告第二台无信号。请求返回成功不能证明实际输出正常。
- 在设备选择前后，`GetDigitalOutMode` 均已返回模式 71、编码 64；这些是该次会话的驱动编号，不是可复用的参数，也不是 CG 模式编号。
- 合盖请求后的端口历史含 Activate=1、SinkActive=1、LaneCount=2、LinkRate=20；共享端口末尾记录与早期真实合盖成功样本相同。历史事件不能证明持续输出或有效画面。
- 共享通道的链路质量读数为 -2；目前未确认该数值的驱动语义，不能直接解释为“断线”“无电”或某种确定的链路故障。正常外屏在两次实验中始终为 100。
- v0.3.2 移除额外的面板关闭请求后，四个对应阶段的显示器、framebuffer、真实合盖状态和共享端口记录均与 v0.3.1 相同。该调整没有改善已采集的输出状态，不能作为修复。

这些数据排除了“本次未执行选择请求”“本次选错 framebuffer”及“没有读到外屏数字模式”，仍未确定实际画面未输出的根因。原始报告保留在本地并由 Git 忽略；这里仅记录诊断所需事实。

## v0.3.2 的恢复失败

v0.3.2 在预览超时后开始恢复。四次恢复尝试均出现以下顺序：

1. 初次内屏启用提交返回 0。
2. 程序重新确认内屏身份、原模式可用且内屏已活动，然后执行额外的内屏禁用，提交返回 0。
3. 再次启用提交返回 1001，恢复失败。

最终报告仅有原先正常的外屏处于活动状态，内屏未恢复。失败发生在额外禁用后的重新启用提交；记录支持移除多余的关屏步骤，但尚未证明该循环是 1001 的底层原因。主程序的后备恢复在守护进程退出后才开始，没有两者同时恢复的证据。

v0.4.0 删除这个额外循环。恢复先启用内屏，再核对活动、唤醒状态和原模式；需要调整模式时单独提交，不再为了刷新配置而把已经启用的内屏关掉。自动核对仍不包含真实像素和色彩，M3 恢复结果需要实机验收。

## v0.4.0 的输出实验（已暂停）

实验先通过 `layout-off` 关闭内屏布局，再提交 `IOMobileFramebufferSetClamshellState(2)`，不额外请求关闭面板。布局禁用本身仍可能使 WindowServer 调整电源；`layout-off` 不表示始终保持供电。常规关闭内屏模式保持原流程。

状态 1 表示开盖，2 表示合盖；系统铰链读数仍反映真实开合状态。接口返回 0 或 1 只记为请求已提交，不能证明输出成功。

若此次切换使第二台外屏新出现在系统中，程序通过 `SLSCopyDisplayInfoDictionary` 的 `IODisplayLocation` 解析其 framebuffer，核对它是否占用已固定的内屏共享通道。CG 显示器 UUID 与 `IOMFBUUID` 不属于相同标识体系；程序不将两者直接比较，也不以 framebuffer 索引代替 CG 显示器 ID。

对应关系明确时，程序向共享通道提交 `IOMobileFramebufferSetDisplayDevice(2)`，随后由新的 `display-rebind` 助手仅对这台新增外屏执行一次禁用、启用配置，两步分别提交给 WindowServer。助手分别固定该外屏的 CG UUID、原生 IOMFBUUID 和 framebuffer 对应关系；停用期间缺少 CG UUID 时，仍必须通过原生身份与通道的唯一匹配，重新启用后必须恢复原 CG UUID。保留现有模式，不直接设置数字输出模式或请求面板电源。原先正常的外屏不参与此次重新配置。没有新增外屏时，例如 M4 启用前已有两台外屏，跳过这一步。

这项实验原本用于检验系统显示配置是否缺少一次完整的重新启用过程。静态分析显示，相同启用状态和相同模式的提交可能被当作无变化，所以直接重复原模式不能保证触发重新配置。这是实验依据，**不是已确认根因或修复结果**。系统也可能在重新配置时读取真实开盖状态。原实现遇到新增外屏身份丢失、通道不再匹配、请求失败或状态未稳定时会中止并请求恢复内屏；本次报告暴露出这一处理不能证明被禁用外屏已重新启用，因此整条实验路径暂停。

M4 实测中，停用后收到配置完成通知；重新启用后则没有新的完成通知，首次完整查询耗时约 3 秒。助手因此在启用阶段保留 5 秒观察窗口，要求同一外屏身份、原模式及活动／唤醒状态连续稳定至少 0.75 秒、至少采样 3 次，且没有正在进行的配置通知；停用阶段仍要求完成通知及实际停用状态。是否收到启用完成通知单独记录，整个助手仍受 10 秒硬期限保护。该核对只验证系统配置，不验证物理画面。

全局显示电源客户端此前在 M3 上的同步、异步开盖预检均返回 1004，未建立连接，因此没有通过该路径提交合盖请求。当前实现不依赖该客户端。

## 原有恢复与画面确认的边界

恢复时先释放软件合盖状态。若本次尝试过外部输出选择，则依次尝试暂停输出（设备 1）、开盖状态 1、内部输出（设备 0）；未尝试选择时不调用额外的设备选择接口。真实盖子仍闭合时，面板恢复等待重新开盖。

唤醒面板前，程序重新找到启用前保存的内屏身份并等待状态稳定。随后启用内屏，并按需从完整模式列表恢复原有分辨率、缩放和刷新率。恢复不依赖旧 CG ID，也不把“请求返回成功”视为恢复完成。自动核对涵盖内屏身份、活动／唤醒状态及原有显示模式，**不涵盖真实像素和色彩**。

原有持续启用模式先进入 30 秒预览，由用户确认画面；未确认、退出或超时会请求恢复内屏。独立守护以及内屏身份、活动状态和原模式核对均不能代替外屏原有输出的恢复验收。本次故障中，退出应用未恢复真实合盖双外屏；不应继续使用重试入口。

## 诊断记录

综合采样保存连续时间线，实验报告保存控制请求及恢复过程，两者在综合报告中一起导出。

每次实验保存实际运行版本、机型、前后 CG ID、固定 framebuffer、选择请求是否执行及原始返回、数字输出模式读数、链路质量和经过字段筛选的端口事件。记录在主进程退出后继续保留，可从菜单导出最近两次。

`GetDigitalOutMode` 仅在读取返回零时记录输出值；这些值、链路质量及 CG 活动标志都不能单独证明画面正常。端口事件明确标为历史数据，不能拿一条旧的 LaneCount 或 SinkActive 事件判断当前有信号。

程序不调用 `GetDigitalOutState` 验收：本机驱动中，这个读取接口还会刷新真实合盖状态，干扰软件合盖请求。报告不包含序列号、EDID、设备 UUID、恢复参数或屏幕内容，不会自动上传。

## 验证范围

- v0.2 的 M3 用户反馈包括第二台外屏无信号和恢复内屏紫屏；真实合盖可恢复双外屏，合盖再开盖可恢复内屏。后续版本的显示列表或模式核对不能代替这些画面的目视验收。
- v0.3 的只读映射已在 M4 / macOS 15.6.1 的内屏和两台外屏上验证，三者都能唯一对应实际 framebuffer，链路读数均为 100。
- 本机 M4 的 `IOMobileFramebufferShim` 对设备选择 0 和 1 返回不支持（`0xe00002c7`）。M3 报告的 `AppleCLCD2` 路径对设备选择 2 和首次暂停输出 1 返回 0、对 0 返回不支持；这些返回值不等于画面结果。
- v0.3 和 v0.3.2 既有 M4 测试包括 30 秒未确认自动恢复、切换中及预览中强杀主程序后的恢复，以及辅助程序运行中强杀守护后的进程清理与恢复。自动核对包含内屏原模式。M3 随后的恢复失败说明这些 M4 结果不能覆盖 M3 的行为。
- 既有恢复实现已修正默认模式列表遗漏当前 HiDPI 模式，以及系统拒绝在同一事务中启用已关闭内屏并设置模式的问题；v0.4.0 继续采用完整模式列表、先启用后按需设置模式的顺序。
- v0.4.0 在 M4 通过了 30 秒未确认预览的自动恢复、切换中及预览中强杀主程序后的恢复。守护异常测试使用独立应用副本，在显示助手写入配置前暂停它，随后结束守护进程；验证待执行助手被清理、没有迟到的合盖请求、内屏原模式恢复。
- v0.4.0 另以独立父进程保护运行生产外屏助手，观察到目标真实停用后重新启用，同一外屏身份及原模式恢复，另一台外屏保持不变，最后内屏原模式恢复。32 项身份／拓扑／提交竞态／完成判断、20 项恢复与预览判断，以及恢复不再禁用内屏的检查通过。
- 综合采样在 M4 的 8 秒只读测试中完成 4 份样本，包含 3 个显示端点、3 条显示通道和 6 个端口；配置回调注册成功，采样前后显示布局与模式一致。12 项扩展字段及隐私检查通过；模拟助手验证了提前停止与回收、6 秒父进程超时、事件／样本／8 MiB 报告上限，以及采样结束后的反馈在保存时补入。本轮未操作真实合盖。
- 新增外屏重新启用路径及取消内屏禁用循环尚未通过 M3 实机验收；本轮 M4 配置检查也未目视确认像素或色彩。

M4 原本就支持开盖双外屏，保留其两台外屏不能证明 M3 已解锁。当前实现也没有验证电气断电、散热收益或 M3 拔线恢复。主要代码位于 [clamshell-driver.m](../Sources/clamshell-driver.m)、[display-link.m](../Sources/display-link.m)、[Routing.swift](../Sources/Routing.swift) 和 [DisplayRecovery.swift](../Sources/DisplayRecovery.swift)。
