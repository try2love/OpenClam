# M3 失败现场与直接合盖路径

2026-09-17 更新：M3 的 v0.3.1 现场报告确认，**第二外屏已映射到正确的共享通道，设备选择请求返回 0，仍没有实际画面**。v0.3.2 移除实验启用过程中额外的面板关闭请求，用于检验共享通道电源状态不同步这一假设；尚无 M3 成功结果。

## 新报告确认的事实

报告来自基础款 M3 MacBook Air（Mac15,12），macOS 26.5.2（25F84），OpenClam 0.3.1：

- 合盖请求后出现第二外屏；它通过 `IODisplayLocation` 唯一映射到启动前固定的内屏共享 framebuffer，选择请求没有跳过或发往另一台外屏。
- `IOMobileFramebufferSetDisplayDevice(2)` 返回 `0x00000000`，随后用户选择了“无信号，恢复并导出报告”。因此请求返回成功与真实无信号发生在同一次实验中。
- 在设备选择前后，`GetDigitalOutMode` 均已返回模式 71、编码 64；这些是该次会话的驱动编号，不是可复用的参数，也不是 CG 模式编号。
- 合盖请求后的端口历史中新增 Activate=1、SinkActive=1、LaneCount=2、LinkRate=20，说明此次请求已伴随端口活动。历史事件仍不能证明持续输出或有效画面。
- 共享通道的链路质量读数为 -2；目前未确认该数值的驱动语义，不能直接解释为“断线”“无电”或某种确定的链路故障。
- 恢复时外部输出暂停返回 0，内部设备选择返回不支持（`0xe00002c7`），后续内屏身份与原模式核对通过。该核对不包含真实像素和色彩。

这些数据排除了“本次未执行选择请求”及“本次选错 framebuffer”，尚不能区分电源状态、持续扫描输出或系统后续重配置的问题。原始用户报告保留在本地并由 Git 忽略；这里仅记录诊断所需事实。

## v0.3.2 的单项调整

v0.3.1 的实验启用先执行显示助手 `off`：关闭内屏布局后，再额外发送 `IOMobileFramebufferRequestPowerChange(0)`。v0.3.2 改为仅执行 `layout-off`，随后沿用合盖请求和输出选择，不增加模式重设或电源开启请求。常规关闭内屏模式保持原流程。

本地 macOS 15.6.1 的 QuartzCore 静态分析显示，WindowServer 会按自身记录的期望／当前电源状态决定是否调用驱动；两者相同时可能跳过请求。应用另行发出的断电请求可能与这份状态记录不同步，导致后续枚举和设备选择成功却没有恢复有效输出。这是本次调整要检验的假设，**报告尚未证明它是根因**。

布局禁用本身也可能使 WindowServer 发送电源关闭请求。因此 `layout-off` 不能理解为“始终保持供电”；本版只是移除应用额外发出的断电请求，让布局变化由系统处理。静态分析来自 M4 / macOS 15.6.1，与故障设备系统版本不同，不能直接当作 M3 的完整执行轨迹。

新版已在 M4 / macOS 15.6.1 连接两台外屏时验证未确认自动恢复，以及切换中、预览中强杀主程序、辅助程序运行中强杀守护后的恢复；核对涵盖内屏活动／唤醒状态和原显示模式。最终验收仍需要 M3 两台外屏实际显示正常画面，并确认恢复后内屏色彩正常。

## v0.3.1 记录范围

每次实验保存实际运行版本、机型、前后 CG ID、固定 framebuffer、选择请求是否执行及原始返回、数字输出模式读数、链路质量和经过字段筛选的端口事件。记录在主进程退出后继续保留，可从菜单导出最近两次。

`GetDigitalOutMode` 返回的是驱动模式编号和编码参数，不是 CG 模式编号。仅在读取返回零时记录输出值；这些值、链路质量及 CG 活动标志都不能单独证明画面正常。端口事件明确标为历史数据，需比较阶段变化；不能拿一条旧的 LaneCount 或 SinkActive 事件判断当前有信号。

早期 M3 样本只包含开盖／真合盖／重新开盖状态。新报告补齐了 v0.3.1 的调用返回和失败现场，并将“无信号”的用户反馈与同一次实验关联；它缩小了排查范围，仍不足以确定根因。

## v0.2 的实机反馈

用户在 M3 上启用 v0.2 后，内屏熄灭，系统列出两台外屏，但第二台没有信号；恢复内屏时还出现紫屏。真实合盖后双外屏正常，合盖再开盖可以恢复内屏。这说明“系统列出两个活动显示器”不足以验收输出或恢复。

v0.3 保留直接合盖请求，增加针对新出现外屏的输出选择尝试，重做内屏恢复，并要求用户确认两台外屏都有正常画面。

## 输出切换与通道核对

v0.3.2 先关闭内屏布局，再提交 `IOMobileFramebufferSetClamshellState(2)`，不额外请求关闭面板。状态 1 表示开盖，2 表示合盖；系统铰链读数仍反映真实开合状态。接口返回 0 或 1 只记为请求已提交，不能证明输出成功。

若此次切换使第二台外屏新出现在系统中，应用通过 `SLSCopyDisplayInfoDictionary` 的 `IODisplayLocation` 解析其实际 framebuffer，核对它是否占用已锁定的内屏共享通道。CG 显示器 UUID 与 `IOMFBUUID` 不属于相同标识体系；程序不再将两者直接比较，也不以 framebuffer 索引代替 CG 显示器 ID。

只有对应关系明确，才向该通道尝试 `IOMobileFramebufferSetDisplayDevice(2)`，请求选择外部输出。接口不支持、拒绝请求或通道无法核对时，中止实验并恢复内屏。M4 启用前已有的两台外屏不会触发这项新输出选择。

`IOMobileFramebufferGetLinkQuality` 仅用于采集当前驱动读数，不证明屏幕已点亮或色彩正确。程序不调用 `GetDigitalOutState` 验收：本机驱动中，这个读取接口还会刷新真实合盖状态，干扰软件合盖请求。历史端口事件也不作为当前输出证据。

## 恢复与画面确认

恢复时先释放软件合盖状态。若本次尝试过外部输出选择，则依次尝试暂停输出（设备 1）、开盖状态 1、内部输出（设备 0）；未尝试选择时不调用额外的设备选择接口。真实盖子仍闭合时，面板恢复等待重新开盖。

唤醒面板前，程序重新找到启用前保存的内屏身份并等待状态稳定。随后从完整模式列表中恢复原有分辨率、缩放和刷新率；有可用外屏且剩余时间足够时，通过实际禁用、重新启用内屏布局完成重新配置。恢复不依赖旧 CG ID，也不把“请求返回成功”视为恢复完成。自动核对涵盖内屏身份、活动／唤醒状态及原有显示模式，**不涵盖真实像素和色彩**。

持续启用模式先进入 30 秒预览。只有用户选择“**两台都有画面，保留**”才继续；选择“恢复内屏”或超时都会触发恢复。超时由独立守护进程执行。外屏全部断开、主程序退出、心跳中断和定时短测结束也会请求恢复；恢复未确认时保留重试入口。

## 验证范围

- 既有 M4 / macOS 15.6.1 测试确认了 v0.2 的关屏、定时恢复和主程序退出恢复；M3 反馈已证明这些测试不能代替实际双外屏画面验收。
- v0.3 的只读映射已在同一 M4 的内屏和两台外屏上验证，三者都能唯一对应实际 framebuffer，链路读数均为 100。
- 本机 M4 的 `IOMobileFramebufferShim` 对设备选择 0 和 1 返回不支持（`0xe00002c7`）。新 M3 报告的 `AppleCLCD2` 路径对设备选择 2 和 1 返回 0、对 0 返回不支持；第二外屏仍无画面。
- v0.3 已在 M4 验证 30 秒未确认自动恢复、切换中及预览中强杀主程序后的恢复，以及辅助程序运行中强杀守护后的进程清理与恢复。最后一项同时检查辅助程序实际加入守护进程组、原辅助进程退出以及内屏原模式恢复。20 项恢复与预览判定测试通过。
- 开发短测发现并修复两处可复现的恢复错误：默认模式列表遗漏当前 HiDPI 模式，以及系统拒绝在同一配置事务中启用已关闭内屏并设置模式。现在读取完整模式列表，先单独提交启用，再按需恢复原模式。M3 紫屏是否因此消除仍未验证。
- v0.3.1 的 M3 失败报告已核对；v0.3.2 的布局关闭调整尚未获得 M3 画面验收，本轮已在 M4 的两台外屏环境验证新流程的未确认自动恢复、主程序及守护异常退出恢复。

M4 原本就支持开盖双外屏，保留其两台外屏不能证明 M3 已解锁。当前实现也没有验证电气断电、散热收益或 M3 拔线恢复。代码位于 [clamshell-driver.m](../Sources/clamshell-driver.m)、[display-link.m](../Sources/display-link.m)、[Routing.swift](../Sources/Routing.swift) 和 [DisplayRecovery.swift](../Sources/DisplayRecovery.swift)。
