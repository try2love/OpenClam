# 直接合盖请求：实现与验证

2026-09-17。此模式已完成 M4 本机短测；**尚未验证基础款 M3 开盖双外屏是否解锁**。

## 与 v0.1 的区别

v0.1 从桌面布局中移除内屏，并请求面板关闭。M3 实测表明，这两步不足以使第二台外屏出现。

本模式增加 `IOMobileFramebufferSetClamshellState` 请求，直接进入显示驱动的合盖处理路径。它不改写铰链传感器，系统的 `AppleClamshellState` 仍反映真实开合状态，也不依赖此前返回 1004 的 `SLSDisplayPowerControlClient` 连接。

实现位于 [clamshell-driver.m](../Sources/clamshell-driver.m) 和 [Routing.swift](../Sources/Routing.swift)。程序使用系统已有接口，无需 root、关闭 SIP、安装内核扩展或修改系统文件。

## 参数、返回值与顺序

在本机 macOS 15.6.1 的系统框架和驱动中确认：状态 **1 表示开盖，2 表示合盖**。驱动行为可概括为：

```c
set_clamshell_state(state) {
    cached_clamshell_state = state;
    if (soft_power_state == 0)
        send_clamshell_state_to_display_controller(state);
    return 1;
}
```

此路径会返回数字 `1`，且不通过该返回值报告显示控制器是否完成路由切换。辅助程序保留原始返回值，并把 `0` 或 `1` 记为 `submitted_not_verified`；只有实际显示器状态满足条件，应用才进入双外屏会话。

操作顺序为：**关闭内屏布局与面板 → 等待电源状态变化 → 提交合盖状态 2**。顺序有意义：面板电源请求会重新读取真实开合状态，可能覆盖先前提交的合盖状态。恢复时先提交开盖状态 1，再开启面板、恢复桌面布局。

上述解释基于 macOS 15.6.1 的本机静态分析；其他系统版本的驱动行为可能不同。本仓库不分发 Apple 系统二进制或反汇编文件。

## 实际验收条件

开始时只要求至少一台外屏可用，以允许 M3 从“内屏＋一台外屏”的初始状态尝试切换。提交后，在限定时间内必须连续观察到：

- 真实铰链保持开盖。
- 内建显示器不再处于活动状态。
- 至少两个不同的外屏 ID 处于活动状态。

没有观察到上述结果就自动恢复内屏，不把“接口调用返回”显示为切换成功。外屏全部断开、主程序退出、心跳中断或试用计时结束也会触发恢复。独立守护进程负责执行并等待控制操作结束，再进行恢复，避免残留的关闭操作与恢复操作交错。

真实合盖时，面板与布局恢复会等到重新开盖。程序不会持续重发合盖请求与系统争抢显示状态。

## 已验证与未验证

本机 M4 MacBook Air、macOS 15.6.1（24G90），连接两台外屏完成了 20 秒短测：

| 阶段 | 内建显示器 | 活动外屏 | 真实合盖标志 |
|---|---|---|---|
| 启用前 | 活动 | 2 台 | false |
| 提交状态 2 后 | 退出活动列表 | 2 台 | false |
| 计时结束并恢复 | 活动且非休眠 | 2 台 | false |

合盖请求和恢复请求均返回 `1`；计时结束后，内屏和两台原有外屏恢复为三个活动显示器。

另外完成了两项实际故障测试：在切换过程中、在启用后分别强制结束主程序，独立守护均恢复内屏。切换中退出的测试发现排队心跳会延迟 EOF 检测；修复为每次读空心跳管道后重跑，确认主程序退出后没有再提交合盖请求。恢复失败状态也会保留在菜单中，允许重试恢复。

M4 原本就支持开盖双外屏，因此这项结果验证了新调用路径能执行、双外屏能保留及计时恢复，**不能单独证明新增请求释放了显示资源，也不能代替 M3 验证**。用户提供的 M3 采样来自 macOS 26.5.2（25F84）；该设备运行本模式后的结果仍待验证。此次短测也不证明面板电气断电、散热改善或实际拔线恢复已完成实机验证。
